MujocoRosUtils Development Roadmap

Planned engineering iterations for modular plugin builds, ros2_control sensor and GPIO interfaces, correctness, reliability, and performance.

Document date: 7 June 2026 Last reviewed: 13 June 2026 ROS 2 targets: Humble and Jazzy Default build: modular plugins Initial I/O scope: numeric and semantic profiles

Executive Summary

Development is divided into three ordered iterations. The first creates independently buildable plugin libraries and a small shared runtime. The second adds ros2_control <sensor> and <gpio> component support through reusable, transport-neutral MuJoCo bindings. The third strengthens correctness, lifecycle behavior, diagnostics, tests, portability, and simulation-loop performance.

The principal architectural rule is one MuJoCo data-access implementation per concept. ROS publishers, ROS subscribers, ros2_control interfaces, recorders, and in-process consumers must reuse shared bindings instead of independently resolving MuJoCo objects or interpreting mjData.

The three core iterations are implemented. Iteration 4 extends the same reuse, validation, and portability rules to the runtime scene, dataset-recording, and visualization subsystems (SceneManager, SimDataAggregator, SimPlotter, and LidarPublisher) that have grown alongside the original scope but were previously tracked only in the README.

Goals and Constraints

  • Rebuilding one MuJoCo plugin must not recompile or relink unrelated plugins.
  • Plugins with heavy optional dependencies must not impose those dependencies on lightweight plugins.
  • Existing MuJoCo plugin identifiers must remain stable.
  • ros2_control <sensor> and <gpio> components must be supported on Humble and Jazzy.
  • Existing publisher and command plugins must be reused through shared backends, not copied into the hardware interface.
  • The initial cross-distribution interface contract is scalar double; typed Jazzy interfaces are a later extension.
  • Simulation-step code must avoid repeated name lookup, unnecessary allocation, and unbounded logging.
  • A monolithic compatibility layout remains available for one release, but modular libraries become the default.

Iteration Sequence

Iteration 2

Ordering constraint: the shared runtime and transport-neutral bindings begin in Iteration 1. Sensor and GPIO support must not be implemented directly inside MujocoSystem before those reusable foundations exist.

Iteration 1: Modular Plugin Builds

Objective

Produce independently compiled and linked MuJoCo plugin libraries while preserving shared process-wide behavior and the existing plugin names used in MJCF.

Target architecture

Core runtime

  • ROS context manager
  • Logging/config helpers
  • Sensor bindings
  • Actuator bindings
  • Data registry
  • Between-step coordination

Independent plugin DSOs

One shared target and one MuJoCo registration entry point per plugin. Each target links only the core runtime and its own direct dependencies.

Optional feature libraries

  • Rendering/depth
  • Recording
  • Plotting UI
  • Scene recompilation
  • ros2_control

Core runtime boundary

Introduce a small shared library, provisionally named mujoco_ros_utils_core. It must contain only facilities that require a single process-wide identity or are reused by multiple plugins:

  • A reference-counted ROS context manager that serializes initialization and prevents one plugin from shutting down contexts owned by another.
  • Common plugin configuration parsing, error reporting, and throttled logging helpers.
  • Out-of-line storage for SimDataRegistry; its singleton must not be duplicated in every plugin DSO.
  • Transport-neutral MuJoCo sensor and actuator binding classes.
  • Between-step registration and state needed by scene-management hooks.

Plugin targets

Create one shared target for every registered MuJoCo plugin. Each target contains its implementation and a small registration translation unit using mjPLUGIN_LIB_INIT. Target and output names should be predictable, for example: 

mujoco_ros_utils_clock_publisher
mujoco_ros_utils_pose_publisher
mujoco_ros_utils_image_publisher
mujoco_ros_utils_actuator_command
mujoco_ros_utils_external_force
mujoco_ros_utils_sensor_publisher
mujoco_ros_utils_lidar_publisher
mujoco_ros_utils_mimic_joint
mujoco_ros_utils_pose_randomizer
mujoco_ros_utils_ros_control
mujoco_ros_utils_sim_data_aggregator
mujoco_ros_utils_sim_plotter
mujoco_ros_utils_scene_manager

The registered identifiers, such as MujocoRosUtils::SensorPublisher, do not change. The library filename is an installation detail and must not leak into model configuration.

CMake interface

Option Default Behavior
MUJOCO_ROS_UTILS_PLUGIN_LAYOUT MODULAR Accepts MODULAR or MONOLITHIC. The two layouts are mutually exclusive in one install tree.
MUJOCO_ROS_UTILS_BUILD_<PLUGIN> ON Controls each plugin target and its dependency discovery.
MUJOCO_ROS_UTILS_ENABLE_CUDA AUTO Controls the image plugin's optional CUDA backend without affecting other plugins.
MUJOCO_ROS_UTILS_BUILD_TESTING Follows BUILD_TESTING Builds registered unit and integration tests.
MUJOCO_ROS_UTILS_BUILD_BENCHMARKS OFF Builds manually invoked performance fixtures without adding them to the pass/fail test suite.

Conditional dependencies

Feature Dependencies Discovery rule
Image publisher OpenGL, GLFW, OpenCV/cv_bridge, image transport, optional CUDA Only when the image plugin is enabled
Plotter SDL2, X11, ImGui, ImPlot Only when the plotter plugin is enabled
Recording HDF5, rosbag2, ament index Only when aggregator recording support is enabled
ROS control hardware_interface, controller_manager, pluginlib, control_toolbox, joint_limits, URDF Only when the ROS control plugin is enabled
Lidar OpenMP when available Optional optimization, not a package-wide requirement

Compatibility transition

  • Modular mode becomes the default.
  • Monolithic mode remains buildable for one release and emits a deprecation notice.
  • Both modes register the same plugin names and accept the same MJCF configuration.
  • Installing both modes into the same plugin directory is rejected because duplicate registration order would be ambiguous.
  • The following release removes monolithic mode after downstream compatibility testing.

Deliverables

  • Core runtime target with exported headers and stable link interface.
  • Reusable CMake helper for declaring and installing one MuJoCo plugin target.
  • One registration entry point per modular plugin.
  • Per-plugin feature flags and conditional dependency discovery.
  • Compatibility monolithic target behind an explicit layout option.
  • Build documentation listing targets, options, dependencies, and install behavior.

Acceptance criteria

  • Touching SensorPublisher.cpp rebuilds the sensor plugin and any directly changed core target, but does not relink image, lidar, plotter, scene, or control plugins.
  • Every plugin library loads independently in a minimal MuJoCo model.
  • A build with only clock and pose plugins enabled does not search for HDF5, SDL2, ImGui, ImPlot, CUDA, or ros2_control.
  • Modular and monolithic test models expose identical plugin names and attributes.
  • Shared registries and ROS context ownership remain process-wide across multiple plugin DSOs.

Iteration 2: ros2_control Sensor and GPIO Support

Objective

Export ros2_control state and command interfaces from <sensor> and <gpio> groups while reusing the same MuJoCo bindings as the existing publisher and actuator-command plugins.

Reuse architecture

MuJoCo bindings Resolve names once, validate dimensions, read sensor data, write actuator controls
→
Consumers SensorPublisher, ActuatorCommand, MujocoSystem, recorder, diagnostics
→
External interfaces ROS topics, ros2_control state/command handles, process-local snapshots

Shared binding APIs

Add transport-neutral value objects to the core runtime. They must not create ROS nodes, publishers, subscriptions, or controller interfaces.

Binding Responsibilities Non-responsibilities
MujocoSensorBinding Resolve a MuJoCo sensor, cache address and dimension, validate an element index, and read scalar or contiguous values. ROS message construction, publishing rate, semantic interpretation
MujocoActuatorBinding Resolve an actuator, cache its ID, validate command range, read control/force state, and write mjData::ctrl. ROS subscriptions, controller ownership, trajectory interpretation
MujocoObjectBinding Optional shared base for model identity, object names, IDs, and validation diagnostics. Generic runtime polymorphism unless it removes concrete duplication

Cross-distribution strategy

  • Build and test against both ROS 2 Humble and Jazzy.
  • Use configure-time feature checks to select the applicable SystemInterface::on_init signature and interface construction API.
  • Generate one private compatibility header; distribution checks must not be scattered through business logic.
  • The portable first milestone supports scalar double interfaces on both distributions.
  • Jazzy typed handles, arrays, and additional data types are deferred to a separate additive milestone.

Sensor profiles

Profile ros2_control interfaces MuJoCo sources
imu orientation.{x,y,z,w}, angular_velocity.{x,y,z}, linear_acceleration.{x,y,z} Frame quaternion, gyro, and accelerometer sensors
force_torque force.{x,y,z}, torque.{x,y,z} Force and torque sensors
range range Rangefinder or another scalar MuJoCo sensor
pose position.{x,y,z}, orientation.{x,y,z,w} Frame position and frame quaternion sensors
generic Arbitrary scalar state-interface names Explicit sensor name and element index for every interface

Portable configuration contract

Component-level parameters are used because they parse consistently on Humble and Jazzy. Interface names remain standard ros2_control names; mappings identify the MuJoCo backing source.

Generic sensor example

<sensor name="tool_feedback">
  <param name="profile">generic</param>
  <param name="state.temperature">mujoco_sensor:tool_temperature[0]</param>
  <param name="state.contact_x">mujoco_sensor:tool_contact[0]</param>
  <param name="state.contact_y">mujoco_sensor:tool_contact[1]</param>
  <param name="state.contact_z">mujoco_sensor:tool_contact[2]</param>
  <state_interface name="temperature"/>
  <state_interface name="contact_x"/>
  <state_interface name="contact_y"/>
  <state_interface name="contact_z"/>
</sensor>

IMU example

<sensor name="base_imu">
  <param name="profile">imu</param>
  <param name="orientation_sensor">base_quat</param>
  <param name="angular_velocity_sensor">base_gyro</param>
  <param name="linear_acceleration_sensor">base_accel</param>
  <state_interface name="orientation.x"/>
  <state_interface name="orientation.y"/>
  <state_interface name="orientation.z"/>
  <state_interface name="orientation.w"/>
  <state_interface name="angular_velocity.x"/>
  <state_interface name="angular_velocity.y"/>
  <state_interface name="angular_velocity.z"/>
  <state_interface name="linear_acceleration.x"/>
  <state_interface name="linear_acceleration.y"/>
  <state_interface name="linear_acceleration.z"/>
</sensor>

GPIO example

<gpio name="vacuum_io">
  <param name="state.pressure">mujoco_sensor:vacuum_pressure[0]</param>
  <param name="state.commanded_level">mujoco_actuator:vacuum_actuator</param>
  <param name="command.level">mujoco_actuator:vacuum_actuator</param>
  <param name="scale.pressure">0.001</param>
  <param name="offset.pressure">0.0</param>
  <state_interface name="pressure"/>
  <state_interface name="commanded_level"/>
  <command_interface name="level" min="0.0" max="1.0"/>
</gpio>

Mapping grammar

Expression Meaning
mujoco_sensor:<name>[<index>] Read one element from a named MuJoCo sensor. Index is mandatory for generic mappings and zero-based.
mujoco_actuator:<name> as state Read the current actuator control value. A later explicit source selector may add actuator force feedback.
mujoco_actuator:<name> as command Write the exported command value to the named actuator's ctrl entry.
scale.<interface> Optional multiplicative conversion applied after reading and before exposing state.
offset.<interface> Optional additive conversion applied after scaling.

Hardware-interface data flow

  • initialize() registers joints, sensors, and GPIOs before any interface vectors are exported.
  • Registration resolves all MuJoCo names and indices once and stores stable backing values for interface handles.
  • read() refreshes joint, sensor, and GPIO state values from cached bindings.
  • write() validates and applies joint and GPIO commands through cached actuator bindings.
  • reset() restores configured initial states and commands for all component groups.

Validation rules

  • Every exported sensor state interface must have exactly one profile-derived or explicit source.
  • Every GPIO state or command interface must have an explicit mapping.
  • Referenced MuJoCo sensors and actuators must exist during initialization.
  • Sensor indices must be within sensor_dim.
  • Semantic profiles must receive the exact required interface set and source dimensions.
  • Duplicate destination mappings and duplicate command ownership are errors.
  • Only double scalar interfaces are accepted in the first cross-distribution milestone.
  • Invalid numeric limits, scales, offsets, and initial values fail initialization with component and interface names in the diagnostic.

Reuse requirements

  • SensorPublisher must delegate MuJoCo sensor lookup and reads to MujocoSensorBinding.
  • ActuatorCommand and MujocoSystem must delegate named actuator resolution and writes to MujocoActuatorBinding.
  • Semantic sensor mappings may compose multiple bindings but must not duplicate address calculation.
  • ROS message conversion remains in publisher plugins; ros2_control handle creation remains in the hardware interface.
  • Images and point clouds remain owned by ImagePublisher and the process-local registry rather than being forced into scalar ros2_control interfaces.

Deliverables

  • Shared sensor and actuator binding APIs with unit tests.
  • Humble/Jazzy compatibility header selected by CMake feature checks.
  • Sensor and GPIO registration, export, read, write, and reset support in MujocoSystem.
  • Semantic profile mapper for IMU, force-torque, range, and pose.
  • Generic scalar mapping parser with scale and offset support.
  • Refactored existing publisher and command plugins using the shared bindings.
  • Example URDF and MJCF pairs for every profile and GPIO direction.

Acceptance criteria

  • ros2_control lists every configured sensor and GPIO interface using the expected component/interface name.
  • IMU, force-torque, range, and pose interfaces match ros2_control semantic component naming.
  • GPIO commands update the configured mjData::ctrl values and honor command limits.
  • Sensor and GPIO states update on each hardware read().
  • A publisher plugin and a ros2_control interface backed by the same sensor report identical values.
  • Invalid mappings fail at initialization, before controllers become active.
  • The complete behavior passes on Humble and Jazzy.

Deferred I/O features

  • Jazzy-native bool, integer, and array handles.
  • Images, point clouds, matrices, strings, and other non-scalar payloads.
  • Dynamic addition or removal of ros2_control interfaces after hardware initialization.
  • Automatic inference of arbitrary semantic profiles from sensor names alone.

Iteration 3: Correctness, Reliability, and Performance

Priority classification

Priority Work Reason
Critical Explicit actuator mappings, command-mode switching, ROS context ownership, reset correctness, mimic-index correction Prevents ambiguous commands, process-wide failures, stale control, and invalid indexing
Essential Effort semantics, lifecycle enforcement, registered tests, portable dependencies, diagnostics Makes behavior inspectable, repeatable, and portable
Good to have Typed Jazzy GPIO, profiling tools, plugin authoring helpers, generated configuration validation Improves scale and developer experience after the contract is stable

Explicit actuator mappings

Replace actuator-name and gain/bias heuristics with explicit joint parameters: 

<joint name="shoulder_joint">
  <param name="position_actuator">shoulder_position</param>
  <param name="velocity_actuator">shoulder_velocity</param>
  <param name="effort_actuator">shoulder_effort</param>
  ...
</joint>
  • Validate that each configured actuator targets the expected joint transmission.
  • Keep heuristic mapping as a deprecated fallback for one release.
  • Emit one initialization warning describing the inferred mapping and the explicit replacement.
  • Reject one actuator being assigned to incompatible command interfaces unless explicitly supported.

Command-mode switching

  • Implement prepare_command_mode_switch() to reject conflicting position, velocity, and effort claims per joint.
  • Implement perform_command_mode_switch() to activate only the selected actuator path.
  • Initialize newly activated commands from current simulated state to avoid discontinuities.
  • Stop writing inactive interfaces even if their command storage still contains values.
  • Define GPIO command ownership through ordinary ros2_control interface claims.

State correctness

  • Report actuator-generated effort from qfrc_actuator when the interface represents simulated actuator effort; reserve qfrc_applied for externally applied forces.
  • Store both MuJoCo object IDs and internal component indices explicitly.
  • Resolve mimic targets to internal vector indices and validate ordering independently of MuJoCo joint IDs.
  • Support mimic offset in addition to multiplier where the ros2_control API provides it.
  • Apply configured min/max constraints consistently to direct and PID-driven commands.

ROS context and lifecycle

  • Move default-context initialization and shutdown into the core runtime.
  • Use reference-counted leases so plugin destruction cannot shut down ROS while another plugin remains active.
  • Allow isolated contexts only for plugins with a documented need, such as independent scene-service lifecycles.
  • Make executor shutdown bounded and join every worker thread before releasing nodes or MuJoCo data pointers.
  • Honor hardware lifecycle states: read while configured, write commands only while active, and clear resources on cleanup.

Reset behavior

  • Perform all mjData mutations on the simulation thread.
  • Restore MuJoCo derived state after an in-step reset before physics continues.
  • Reset joint, sensor, and GPIO backing values to configured initial values.
  • Clear stale actuator commands and PID integrator/history state.
  • Reset controller timing when simulation time moves backward.
  • Test service-driven, viewer-driven, and direct MuJoCo resets.

Performance and scale

  • Resolve object names, sensor addresses, joint addresses, and actuator IDs only during initialization or model recompilation.
  • Preallocate state, command, message, and diagnostic storage before the update loop.
  • Avoid per-step string streams and message-vector resizing.
  • Publish debug command topics only when enabled by configuration.
  • Keep camera frame copies sequence-gated and make process-local callbacks execute outside registry locks.
  • Measure controller update duration, read/write duration, missed periods, and simulation real-time factor.
  • Use throttled diagnostics and compile-time or runtime disabled fast paths.

Portability and packaging

  • Replace hard-coded HDF5 paths with imported CMake or pkg-config targets.
  • Permit system-provided or vendored ImGui/ImPlot without mandatory network access during every clean configure.
  • Install plugin libraries to a package-owned directory and provide an environment hook extending MUJOCO_PLUGIN_PATH.
  • Set relocatable RPATH values and test installation outside the MuJoCo source or binary tree.
  • Generate a machine-readable plugin manifest containing library names, registered plugins, dependencies, and build options.

Diagnostics

  • Publish or expose initialization status, active interface modes, and mapping summaries.
  • Report read, update, and write durations with configurable thresholds.
  • Count missed controller updates, late callbacks, invalid commands, and reset events.
  • Include component and interface names in all validation failures.
  • Keep diagnostics disabled or allocation-free in the hot path when not requested.

The first diagnostics increment is implemented through MujocoSystemInterface::diagnostics(). Set the ros2_control hardware parameter diagnostics_enabled to true to collect monotonic read and write durations. Operation, reset, invalid-command, and missed-period counters are exposed in the same snapshot. Timing clock calls are skipped when diagnostics are disabled.

Benchmark fixture

Configure with -DMUJOCO_ROS_UTILS_BUILD_BENCHMARKS=ON to build the standalone read/write benchmark. It is intentionally excluded from CTest because throughput thresholds depend on the host, build type, middleware, and system load. Record the build type, iteration count, CPU, MuJoCo version, and ROS distribution with every result.

Good-to-have follow-up features

  • Jazzy typed GPIO handles for Boolean and integer I/O while preserving the portable double contract on Humble.
  • A plugin-authoring CMake template and registration helper.
  • A configuration linter that checks URDF mappings against an MJCF model without starting a simulation.
  • Benchmark fixtures for large joint counts, high-rate lidar, multiple cameras, and multiple controller managers.
  • Generated reference pages for plugin attributes and ros2_control mapping parameters.

Iteration 4: Scene, Recording, and Visualization Subsystems

Objective

The runtime scene, in-process recording, plotting, and lidar subsystems are already shipping and documented in the README, but they predate or sit outside the original three-iteration contract. This iteration brings them under the same rules the rest of the roadmap enforces: reuse of shared MuJoCo bindings, explicit validation, opt-in diagnostics, and registered CI coverage. No new plugin is required; the work is consolidation and hardening.

Reuse constraint: recorders and plotters must read MuJoCo state through MujocoSensorBinding, MujocoActuatorBinding, and the process-local registry, never by independently resolving names or indexing mjData. This keeps Iteration 4 aligned with the single data-access principle in the executive summary.

Scene management (SceneManager)

  • Run every mjData mutation and mj_recompile on the simulation thread through the between-step hook, and document the requirement that scene edits are unsafe mid-step.
  • Validate spawned MJCF/URDF (name collisions, free-joint requirements, mass/inertia sanity) before recompilation rather than failing inside the physics step.
  • Make spawn/despawn transactional so a failed recompile restores the prior model and simulation state instead of leaving a partially mutated scene.
  • Preserve qpos/qvel for unaffected bodies across recompilation and add a regression test asserting state continuity.
  • Add services for attach/detach (weld) and equality-constraint introspection that complement the existing SetEqualityActive.
  • Optionally serialize the accumulated runtime edits back to an MJCF snapshot for reproducibility.

Recording (SimDataAggregator and SimRecorder)

  • Read joint, actuator, and sensor streams through the shared bindings so recorded values match publisher and ros2_control values exactly.
  • Version the HDF5 and LeRobot layouts and write a schema/version attribute so downstream loaders can detect format changes.
  • Support segmented or resumable episodes and bound memory for long recordings instead of growing unboundedly.
  • Expose recording health (queued frames, dropped frames, encoder backlog, async-video status) through the same diagnostics snapshot used by the hardware interface.
  • Provide a single trigger that starts and stops recording across multiple aggregator instances atomically.
  • Keep the NVENC-to-software encoder fallback covered by a CI path that exercises the software encoder.

Visualization (SimPlotter)

  • Allow plotting of ros2_control interfaces and diagnostics counters, not only raw qpos/qvel/sensor sources.
  • Add a headless/offscreen capture mode so plotting can be smoke-tested in CI without a display server.
  • Persist and reload plot configurations so layouts survive simulator restarts.
  • Keep the SDL/OpenGL thread isolated from the physics thread and document the GPU (EGL/GLX) versus software fallback selection.

Lidar (LidarPublisher)

  • Optionally accelerate ray casting (OpenMP already; evaluate a CUDA path that reuses the image plugin's CUDA selection).
  • Add intensity and ring channels and a configurable point type for VLP-style output.
  • Provide benchmark fixtures for high-ray-count, high-rate configurations under the existing benchmark flag.

Cross-cutting manifest

  • Complete the machine-readable plugin manifest carried over from Iteration 1 and extend it to advertise each plugin's ROS topics, services, and parameters.
  • Expose a runtime discovery service that lists active plugin instances and their resolved node and service names, replacing ros2 service list | grep guidance in the README.

Deliverables

  • Scene mutation validation, transactional recompile, and state-continuity tests.
  • Recorder format versioning, bounded buffering, and recording-health diagnostics.
  • Plotter headless-capture mode and configuration persistence.
  • Lidar channel extensions and benchmark fixtures.
  • Completed plugin manifest and runtime discovery service.

Acceptance criteria

  • A recorder and a publisher backed by the same source report identical values.
  • A failed spawn leaves the model and simulation state unchanged.
  • Scene edits preserve the state of unaffected bodies across recompilation.
  • Recording-health and plotter state are observable without a debugger.
  • The plotter and a minimal scene/recording scenario run in CI without a physical display.

Required scenarios

  • Humble and Jazzy builds in modular mode.
  • Humble and Jazzy builds in monolithic compatibility mode.
  • Minimal clock-only build without optional graphics, recording, plotting, or control dependencies.
  • Every sensor semantic profile with valid and invalid dimensions.
  • GPIO input-only, output-only, and bidirectional components.
  • Conflicting controller command modes and successful mode transitions.
  • Multiple plugin and controller-manager instances in one process.
  • Reset during active control with no stale command reapplication.
  • AddressSanitizer, UndefinedBehaviorSanitizer, and ThreadSanitizer jobs where supported.
  • Installed-tree plugin discovery with no source-tree paths.
  • Runtime scene spawn/despawn with state continuity for unaffected bodies and rollback on failed recompile.
  • Recorder/publisher value parity and a headless plotter/recording smoke test without a display server.

Risks and Mitigations

Risk Impact Mitigation
Singleton duplication across plugin DSOs Registries and context ownership diverge by library Move state to an out-of-line core shared library and test cross-DSO identity
Duplicate plugin registration Undefined library-load behavior Make modular and monolithic install layouts mutually exclusive
Humble/Jazzy API drift Conditional code spreads through the hardware implementation Use configure-time feature checks and one compatibility adapter
Sensor naming ambiguity Incorrect semantic values Require explicit profile sources or explicit generic mappings and validate dimensions
Multiple writers to one actuator Last-write-wins commands and unstable simulation Validate ownership and enforce ros2_control command-mode claims
ROS shutdown from one plugin Other plugins lose nodes, services, and executors Reference-counted core context manager and isolated contexts only where necessary
Modular build increases installation complexity Plugin paths and RPATH become fragile Package-owned install directory, environment hook, relocatable RPATH, installed-tree tests

Definition of Done

The roadmap is complete when all of the following hold:

  • Plugins build and load independently, with optional dependencies isolated.
  • The shared runtime provides one ROS lifecycle and one process-local registry identity.
  • Joint, sensor, and GPIO ros2_control interfaces operate on Humble and Jazzy.
  • Existing ROS plugins and ros2_control reuse the same MuJoCo binding code.
  • Actuator mapping and command ownership are explicit and validated.
  • Reset, lifecycle, and multi-instance behavior are covered by automated tests.
  • Hot paths avoid repeated lookups, unnecessary allocation, and uncontrolled logging.
  • The installed package is relocatable and does not rely on hard-coded system paths.
